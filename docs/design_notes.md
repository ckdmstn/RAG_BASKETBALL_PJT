# KBL RAG 설계 메모 (진행하면서 계속 채운다)

> 최종 제출물(요구사항 정의서, RAG 파이프라인 설계문서)의 재료. 결정할 때마다 "왜"를 한 줄씩 적는다.

## 1. 도메인 (PDF 2.1)
- 도메인: 한국 남자 프로농구(KBL) 2026-27 시즌 선수·팀·규정
- 항목 메타데이터: 선수 186명(10개 구단), 팀 정보 10건 → 100건 이상 충족
  - 출처: 웹 검색 가능한 AI가 나무위키·언론 기사 등을 참고해 정리 (기준일 2026-09~10), 항목마다 source_urls 보유
  - 이용 조건: 개인 학습용. 값의 정확성보다 "문서에 적힌 대로 답하는 RAG" 연습이 목적
- 외부 문서 출처
  - 한국어 위키백과 (MediaWiki API, CC BY-SA 4.0, 출처·링크 표시) — 팀/대학/드래프트/리그/선수 본인 문서
  - KBL 공식 규정 PDF (외국선수 관리규정, 자유계약선수 관리규정, 선수등록규정, 선수 보수 규정) — 한국농구연맹 공식 사이트 공개 자료, 개인 학습용
- 근거가 필요한 질문 (정답은 색인된 문서 기준)
  1. 박정웅은 몇 년도 드래프트에서 몇 순위로 어느 팀에 지명됐어?
  2. 서울 SK 나이츠는 챔피언결정전에서 몇 번 우승했어?
  3. KBL에서 외국인 선수는 최대 몇 명 등록할 수 있어?
  4. (선수 선택 후) 이 선수의 출신 대학은 어디야?
- 위험 도메인 여부: 아님 (면책 문구 불필요)
- 선수 본인 위키 문서가 없는 선수: 소속 팀·대학·리그 문서와 메타데이터 청크를 근거로 삼고, 문서에 없으면 "확인되지 않는다"고 답함 (강사님 확인 완료 2026-10-21)

## 2. 항목 텍스트 설계 (PDF 2.2)
- 선수 1명 = 하나의 글. 필드가 짧아서 **모든 필드 포함**
- 쓰는 법: 불리언은 말로(국내 선수/외국인 선수), 숫자에는 단위(194cm, 등번호 4번), null인 값은 줄째 생략
- 동명이인(이정현, 최승욱)은 팀·등번호·출생년도·출신 학교가 글에 들어가 구분됨. 식별자는 이름이 아니라 player_id(팀코드-등번호)

```
선수: 박정웅 (안양 정관장 레드부스터스, 등번호 4번)
포지션: 가드 / 국내 선수
신체: 194cm, 81kg / 출생: 2006년
출신: 홍익대학교사범대학부속고등학교
드래프트: 2024 KBL 신인선수 드래프트 1라운드 1순위 (안양 정관장)
경력: ...
```

## 3. 컬렉션과 메타데이터 설계 (PDF 2.3)
### kbl_players  (선수 1명 = 청크 1개, 청크 ID = player_id → 다시 색인해도 덮어쓰기만)
- 메타데이터: player_id, name, team, position, is_foreign, jersey_number, (birth_year, school 은 값이 있을 때만)
- ChromaDB 메타데이터는 null·목록을 못 넣는다 → 코드에서 걸러낸다

### kbl_docs  (위키/PDF 청크)
- 메타데이터: doc_title, source_url, doc_id, source_type(wiki/pdf), scope(player/team/league),
  player_id(scope=player 일 때), team(scope=team 일 때), collected_at, chunk_seq
- 청크 ID: `{scope}:{doc_id}:{순번}` (scope를 넣은 이유: 같은 문서가 서로 다른 scope로 저장돼도 id가 겹치지 않게)
- 청크 텍스트: `[문서 제목]\n본문 조각` (조각만으로도 어느 문서인지 알 수 있어 검색이 정확해짐)
- scope 규칙(코드): 선수 본인 문서=player / 제목이 10개 팀 중 하나와 같음=team(그 팀 꼬리표) / 그 외=league. 본인 문서가 아닌 500자 미만 문서는 제외
- 검색 필터: (player_id == 선택 선수) OR (team == 선수 팀) OR (scope == league)  ← 4단계에서 효과 확인

## 4. 겪은 문제와 해결 (설계문서 "겪은 문제, 해결 과정"의 재료)
- 2026-10-21 | AI가 만든 선수 JSON 파일 끝에 {"sources_summary"}, {"notes"} 줄이 붙어 json.load 실패
  → clean_kbl_data.py 가 여러 JSON 값을 순서대로 읽어 분리
- 2026-10-21 | 동명이인(이정현 2명, 최승욱 2명) → 이름 대신 player_id(팀코드-등번호)
- 2026-10-21 | AI가 채운 ko_wiki_title 신뢰 불가 (직접 확인 안 했다고 밝힘) → 코드가 위키 API로 판정
- 2026-10-21 | 이름 그대로의 위키 문서는 동음이의/타인 문서일 수 있음 (예: 박찬호) → 분류에 '농구'가 있는지로 판정
- 2026-10-21 | KBL 규정 PDF에서 "제 1 조"의 번호가 본문과 떨어져 추출됨 (pypdf, pymupdf 둘 다)
  → 해결 예정: 정규식으로 조 번호 복원 후 조 단위 청킹 (위키는 글자 수 단위 청킹 → 출처 종류별 청킹 이유로 설명 가능)
- 2026-10-21 | 팀 문서를 선수 21명 몫으로 복제하면 임베딩 토큰 21배 → scope 꼬리표로 한 번만 저장
- 2026-10-22 | 의미 검색 실험 ("고려대 출신 가드"에서 5명 중 2명만 정답, "키가 큰 선수"는 실패, 동명 검색에서 비슷한 이름 다른 사람 혼입)
  → 원인: 임베딩은 의미가 비슷한 후보를 가져올 뿐 조건 정확도·숫자 크기·고유명사 일치에 약함, k는 항상 개수를 채움
  → 해결 방향: 꼬리표 필터(team/position/is_foreign, player_id) + 후보를 넉넉히 가져와 LLM이 선별(F2011) + 숫자 비교는 코드로 정렬
- 2026-10-22 | 색인 재실행 시 임베딩 낭비 → 저장된 글과 같으면 건너뜀(텍스트 기준 비교). 한계: 꼬리표만 바뀐 경우는 감지 못함
- 2026-10-22 | 수집 캐시가 "검색어 → 선별된 문서"를 기록해서, 첫 질문에서 아무것도 선택되지 않으면 다음 질문도 건너뛰어 문서를 못 가져옴
  → 원인: 선별은 질문에 따라 달라지는데 캐시가 그 결과를 고정함
  → 해결: 질문과 무관한 것(검색 결과 후보, 문서 본문)만 캐시하고, 후보 선별은 질문마다 실행
- 2026-10-22 | 프롬프트 2가 다른 팀 문서(원주 DB)와 동명이인 문서(드라마 '전우')를 선택
  → 원인: LLM 판단은 어겨질 수 있고, 선택된 문서를 전부 '내 팀 문서'로 붙이던 것도 문제
  → 해결: 코드 규칙 (제목이 선수 팀 이름과 같을 때만 scope=team, 아니면 league / 본인 문서 외 500자 미만은 제외)
- 2026-10-22 | 필터 없는 검색에서 정관장 질문에 LG 문서 청크가 1~2등으로 나옴, 그리고 같은 질문인데 실행마다 프롬프트 2가 다른 문서를 선택
  → 원인: 임베딩은 의미 유사도만 보고, LLM 선별은 실행마다 흔들림
  → 해결 방향: 4단계에서 scope/team/player_id 필터로 후보 범위를 코드로 제한
- 2026-10-22 | LLM이 소속 팀 문서를 버리고 다른 팀 문서를 선택 → 소속 팀 문서는 코드가 강제 포함, 다른 팀 문서는 후보에서 제외

## 5. 프롬프트 3개 (PDF 2.4)
- 프롬프트 1 검색어 추출: KBL 전문 사서. 입력=선택 선수 정보+질문. 출력=JSON 배열(검색어 2~4개, 짧은 명사: 인물+주제+소속팀).
  선택 선수 이름은 LLM과 무관하게 코드가 항상 추가(F2003). "이 선수" 같은 지시어를 풀기 위해 선수 정보를 같이 전달.
- 프롬프트 2 후보 선별: 입력=질문+후보(번호, 제목, 앞부분 요약). 출력=JSON 번호 배열(없으면 []).
  본문 전에 선별 → 버릴 문서의 본문을 LLM에 넣는 토큰 낭비를 방지.
- 프롬프트 3 답변 생성: 근거만 사용, 주장마다 [근거 n], 근거에 없으면 "문서에서 확인되지 않는다".
  근거 안의 지시문은 따르지 않음. 코드는 답변의 [근거 n]을 파싱해 실제 인용된 근거만 화면에 표시(F2008).

## 6. 서비스 기능과 화면 (PDF 2.6)
- 도메인 특화 기능(F2010): 팀 가이드. 팀 선택 → 정해진 형식(연고지·홈구장 / 역사 / 주요 성적 / 현재 선수단)으로 요약.
  근거 = 팀 정보(kbl_teams.json) + 위키백과 팀 문서 + 선수 메타데이터(팀 필터). 근거 없는 항목은 "확인되지 않음".
  선택 이유: 이미 확보한 데이터를 그대로 쓰고, 근거 출처가 3종류로 섞여 근거 표시·필터 검색을 연습하기 좋음.
- 조건 기반 탐색(F2011): 자연어 조건 → 선수 메타데이터 후보 검색 → LLM이 조건에 맞는 선수만 선별 → 카드 → 클릭 시 대화로 연결.
- 진행 상태·안내(F2012): 처리 중 표시 / 색인 없음 / API 키 없음 / 검색 결과 없음. 위험 도메인 아님 → 면책 문구 없음.
- 검색 설정(시작값, 단계 3에서 확인하며 조정): 청크 1000자 / 중복 200자 / Top-k 6 / 유사도 검색
  → 단계 4 검증 질문 통과로 1000/200, Top-k 6 확정
- 근거는 코드가 직접 모음(id 조회 / 팀 필터 검색 / 선수단 요약은 코드 계산)
- 구현: 조건을 LLM이 JSON으로 번역 → 코드가 검증·필터·정렬(팀, 포지션, 외국인 여부, 학교, 키·몸무게·출생 연도) → 경력 키워드가 있으면 그 범위 안에서 의미 검색(상위 10명) + LLM 선별. 화면은 탭 대신 radio로 나눔(카드 클릭 → 대화 화면 이동을 코드로 하기 위해)

## 7. 알려진 한계
- 캐시는 검색어 문자열이 똑같아야 적중한다. LLM이 매번 다른 검색어를 만들면 일부만 적중한다.
- 500자 미만 위키 문서(본인 문서 제외)는 버리므로 짧지만 유용한 문서도 놓칠 수 있다.
